# 大模型协作记录

> 本文档如实记录本项目开发过程中人与大模型（Claude Code，基于 Anthropic Claude 的 Agent 式 CLI）的协作方式、分工与正确性保障，供竞赛「大模型辅助设计」评审。

## 1. 协作模式与分工

采用「人定方向、模型执行、人验收」的协作模式：

- **人**：负责需求定义、架构决策、硬件事实确认、物理操作（插卡/上电/舵机）、最终验收。
- **大模型**：负责代码/脚本编写、构建调试、日志分析、批量文件整理与文档生成；**不越权做物理操作，不虚构测试结果**。

关键决策均由人拍板，模型只提供分析与建议。例如：是否升级 Vivado 2023.2、是否采用单 RP 双 RM、竞赛交付包按哪个目录模板——这些是人的决策，模型负责执行与记录。

## 2. 大模型承担的工作

| 阶段 | 内容 |
|---|---|
| DFX 位流构建 | 编写/维护 `dfx320.tcl`；定位 0 帧空 partial 的根因（2022.x 工具 bug）；定位浮点核加密密钥滚动与模块名 rev 升级两个连锁坑；编写 `replace_fp2023.ps1` 一键换库脚本；处理 cell 句柄失效等 Tcl 细节 |
| 构建监控 | 编写监控脚本周期性拉取 Windows 构建机日志、判定 `DFX_BUILD_OK`/ERROR 状态 |
| 软件适配 | 定位 wm 地址迁移（hwh / wm_accelerated.py / modes.json 三处）、位流替换、package_manifest sha256 同步 |
| 镜像注入 | 编写 `inject_dfx_partial.sh`，挂载镜像 p2 写文件，重挂只读全量校验 manifest |
| 打包交付 | 按 AMD 选题指南目录模板整理 src/sim/build/board/data/skill/report，写 README 与设计报告 |

## 3. 人承担的工作

- 确认硬件事实：器件型号（xc7z020）、舵机映射、摄像头引脚、标定数据等——这些来自人的实测，模型不臆造。
- 架构决策：DFX 单 RP 双 RM、地址规划、加载路径选型。
- 物理操作：SD 卡写入、上电验收、舵机/相机实测。
- 最终验收与发布。

## 4. 正确性保障

1. **不虚构结果**：模型被明确约束「不虚构硬件/测试结果」。
2. **工具链级验证**：位流用 Vivado `pr_verify`（静态区一致性）、时序报告（Setup/Hold 0 失败端点）验证；软件用 sha256 全量校验（package_manifest 1585 条目 0 不匹配）。
3. **镜像安全**：原始镜像不变（只改副本）；泄漏的 GitHub PAT 在打包时逻辑 + 物理双重清除。
4. **可复现**：所有脚本（dfx320.tcl、replace_fp2023.ps1、inject_dfx_partial.sh、switch_fast.py）入库，构建/部署步骤写入 README。

- 2026-11-04：首次 DFX 构建，partial 位流仅 314 B（0 帧），误判为成功；`pr_verify` 通过 ≠ 位流非空，吸取教训。

## 6. 反思与边界

- 大模型在「多版本工具链 + 加密 IP + DFX」这类组合坑上有效，但每一步都必须有**可验证的产物**（位流大小、pr_verify、sha256）背书，不能只看日志里的成功字样。
- 大模型的边界在于**物理世界**：上板验收、真实机械臂动作、标定精度等，必须由人完成并确认。
